Requirements Specification

We wrote the requirements loosely following IEEE Std 830 ieee830. There are three kinds of users. A user holds a wallet and sends money. An analyst can do everything a user can, and also reviews alerts. An admin can do everything an analyst can, and also manages rules, thresholds, the model, the simulator and system health.

Hardware and Software Requirements

For development and the demo, a machine with a 4-core 64-bit CPU, 8 GB RAM and about 10 GB of free disk is enough. We used an Apple silicon laptop. The client can be any modern browser, desktop or mobile. A pilot would need around two 4 vCPU / 16 GB virtual machines plus managed PostgreSQL and Redis.

On the software side, the stack runs on Docker with Compose v2 on macOS, Linux or Windows (WSL2). It uses Node.js 20 or later with TypeScript, Next.js 15 and React 19 for the web app, Express with Prisma for the API, Python with FastAPI and scikit-learn 1.6 for the ML service, PostgreSQL 16 and Redis 7. Testing uses Vitest, pytest, Playwright and autocannon.

Constraints and Assumptions

The main constraints were that we had no access to a real payment network or real fraud data, that the core build had to be done in about one week, that scoring had to be fast enough for a live payment, and that the whole thing had to run on one laptop for the demo. A real deployment would also have to meet RBI, NPCI and DPDP rules (Chapter 7).

We assumed that all time-of-day features use IST, that the maximum payment is ₹1,00,000, and that the device sends a stable random ID which the server only stores as a hash. "Payee age" means days since the payee was first seen on our platform. Failed attempts include both wrong passwords and wrong UPI IDs at the re-type step. We also assumed that answers to the questions might not be truthful, and that only an analyst's verdict, not user reports alone, can block a payee.
