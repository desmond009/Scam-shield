Requirements Specification

This chapter specifies the software requirements following the structure recommended by IEEE Std 830 ieee830. Requirements are identified so that they can be traced to design elements (Chapter 8) and test cases (Chapter 10). Priorities use the MoSCoW scheme (M = must, S = should, C = could).

Functional Requirements

Functional requirements
IDRequirementPriority
Accounts and wallet
FR-1The system shall allow a person to register with name, e-mail and a password of at least 8 characters, assign a UPI ID and credit synthetic starting balance (₹25,000).M
FR-2The system shall authenticate users and maintain a session using an httpOnly cookie, and shall count failed logins as a risk signal.M
FR-3The system shall show balance, 30-day spending by day, transaction history (filterable by status and risk band) and number of warnings received.M
FR-4The system shall let a user look up a payee and see display name, age on the platform, report count and whether the user has paid them before.S
Risk check and payment
FR-5On a payment request, the system shall compute the 20 defined features from the user's and payee's state without moving any money.M
FR-6The system shall evaluate all enabled rules, obtain a calibrated ML probability, blend them into a 0–100 score and assign a band using configurable thresholds.M
FR-7The system shall apply hard overrides: confirmed scam payee → score ≥ 95 and blocked; OTP/app-install request → at least HIGH.M
FR-8The system shall return reason codes, a one-line summary and the top three plain-language reasons with every decision.M
FR-9The check endpoint shall be idempotent with respect to an Idempotency-Key header.M
FR-10The system shall issue a signed check token (10 minutes) binding user, transaction, amount and payee; confirm shall require it.M
FR-11For LOW risk the payment shall proceed with no additional step.M
FR-12For MEDIUM risk the UI shall show the warning, reasons and three yes/no questions; answers shall re-score the payment and may only raise the score.M
FR-13For HIGH risk the system shall enforce a 10-second cooldown and require the payee UPI ID to be retyped exactly before confirm succeeds.M
FR-14Confirm shall debit the payer, write ledger entries, credit a platform payee and mark the transaction completed atomically, and shall prevent double spending.M
FR-15The user shall be able to cancel a pending payment and optionally report the payee; each user may report a payee once.M
Analyst and admin
FR-16MEDIUM and HIGH decisions shall create alerts that appear in the analyst console in real time.M
FR-17The analyst shall see features, all reasons with technical detail, ML top contributing features and payee history, and record a FRAUD or SAFE verdict with notes.M
FR-18A FRAUD verdict shall label the transaction, mark the payee as confirmed fraud and update its reputation.M
FR-19The admin shall enable/disable rules and edit their weights and parameters, blend weights and band thresholds at runtime, with a what-if preview on labelled holdout data.S
FR-20The admin shall trigger retraining using synthetic data plus analyst labels and view the evaluation of the active model.S
FR-21The admin shall run scam scenarios (normal, impersonation, mule, velocity, takeover) through the real pipeline.S
FR-22The admin shall view system health: service status, decisions by band, latency percentiles, ML outcomes and breaker state, queue depths.S
FR-23Security-relevant administrative actions (verdicts, rule changes, retraining, simulator runs) shall be written to an audit log.M

Constraints and Assumptions

Constraints

  • No real payment network or data. Students cannot connect to NPCI or obtain bank fraud data, so all users, money and fraud cases are synthetic.
  • Time. The core build had to be completed within a one-week sprint, which favoured simple, well-understood components over breadth.
  • Latency. Scoring must fit inside a real-time payment flow; this rules out heavy models and slow explanation methods at request time.
  • Hardware. Everything must run on a single laptop for the demonstration.
  • Regulation. A production deployment would be subject to RBI, NPCI and DPDP Act obligations (Chapter 7) which a student prototype cannot meet in full.

Assumptions

  • All hour-of-day features use Indian Standard Time; the maximum payment is ₹1,00,000.
  • The payer's device sends a stable random identifier; the server stores only its hash.
  • payee_age_days is time since the payee was first seen on the platform (0 if never).
  • failed_attempts_15min counts failed logins plus failed recipient-retype checks.
  • Questionnaire answers are voluntary and may be untruthful; they can therefore only increase risk.
  • Analyst verdicts are authoritative for blocking a payee; user reports alone never block.
