System Design and Technical Details

System Architecture

ScamShield runs as six Docker containers started together with Docker Compose docker (Figure 8.1). The web container is the Next.js front end. It also forwards /api calls to the API, so the login cookie stays on the same site. The api container is a stateless Express server that handles login, payments, alerts and admin functions. The worker uses the same code but runs background jobs. The ml container is a FastAPI service that trains the model on first start and then answers scoring requests. PostgreSQL is the main database and Redis holds fast-changing state like counters, caches, rate limits and job queues.

The main design idea was to keep the "hot path", everything needed before the payer sees a result, as short as possible. Anything that does not change the current decision (creating alerts, refreshing baselines, updating payee reputation, metrics, retraining) goes to a queue and is done by the worker.

Database Schema

The main tables are User (role, UPI ID, balance, hashed registered device), Payee (every UPI ID ever paid, with first-seen date, report count, reputation and a confirmed-fraud date), Transaction (amount, payee, status, FRAUD/SAFE label, idempotency key), RiskDecision (rule, ML and final scores, band, reasons and features as JSON, model version, latency), Alert, LedgerEntry (every balance change with the balance after it) and PayeeReport. Smaller tables hold rule settings, thresholds, model versions and the audit log. There is a unique index on (user, idempotency key) so a payment cannot be created twice, and indexes on user and payee by time for the history lookups. The Redis keys are listed in Appendix B.

Algorithms and Business Rules

Features

The 20 features are computed by the same logic in TypeScript (for serving) and Python (for training), both reading one shared JSON spec. A test with 300 random inputs checks that both give exactly the same values. The amount z-score compares the payment with the user's last 30 days, z = (a − μ) / max(σ, 0.1μ, 50), limited to the range −5 to 20. The floor on σ stops users with very regular payments from getting huge z-scores. The user's usual payment hour is a circular mean, so 11 pm and 1 am average to midnight and not noon. Velocity counts payments in the last 10 minutes and 1 hour. The mule signal counts how many different people paid the payee in the last 24 hours. The three questionnaire answers are features too, and they stay 0 until answered.

The rule score is the sum of points (each multiplied by its weight), capped at 100.

Model

We use scikit-learn's HistGradientBoostingClassifier, a gradient boosted tree model friedman2001, with 300 iterations, learning rate 0.08, 31 leaves per tree, L2 regularisation of 1.0 and balanced class weights. Class weighting pushes the probabilities too high, so we calibrate the output with isotonic regression zadrozny2002, niculescu2005 on a separate, later slice of time. The ML score is the calibrated probability × 100. To explain a single decision we use occlusion. We make 20 copies of the payment, each with one feature reset to a typical genuine value, and see how much the fraud probability drops. All 21 rows are predicted in one call, so it is cheap.

Blending and overrides

Final score = 0.4 × rule score + 0.6 × ML score (rule score alone if ML is unavailable)

A final score below 35 is LOW, 35 to 69 is MEDIUM and 70 or above is HIGH. If an analyst has confirmed the payee as a scam, the score is raised to at least 95 and the payment is blocked. If the user says they were asked for an OTP or to install an app, the score is raised to at least 70. After the questionnaire, the new score is never allowed to be lower than the old one. The reasons are ordered with overrides first, then rules by points, then "matches known scam patterns" if the ML score is 50 or more.

Reliability

The ML call has a 150 ms timeout and a circuit breaker nygard2018. If it fails 5 times within 30 seconds, we stop calling it for 15 seconds and use rules only. After that, one test request (chosen with a Redis lock) decides whether to start calling it again. The breaker state is in Redis, so all API instances share it. The Idempotency-Key is claimed in Redis with SET NX for 24 hours kleppmann2017: a repeat with the same body gets the stored response, a different body gets 422, and a duplicate arriving at the same moment gets 409. Confirm runs in one database transaction with two conditional updates. The first, status = 'PENDING', means only one confirm can win. The second, balance ≥ amount, means the balance can never go negative. If anything fails, everything is rolled back.

Synthetic Data Generation

Since we had no real fraud data, we wrote a generator with a fixed seed (42). It simulates 150 users of the four persona types from Chapter 3 (50 salaried, 40 students, 30 shopkeepers, 30 seniors) over 120 days. The first 30 days are only used to build up history, and the remaining 90 days give about 165,000 payments. There are 1,500 merchants with a Zipf popularity curve, and 20 % of them open during the simulation.

We spent a lot of effort on genuine payments that look suspicious, because without them any detector looks better than it is. These include rent of up to ₹25,000 once a month, two festival periods with bigger and more frequent payments and pop-up stalls paid by many people, first purchases from new shops, shopkeeper supplier batches, students paying late at night, new phones and login typos. About 2.4 % of payments are fraud, spread over four scenarios: impersonation (new payee, amount 3 to 40 times usual, follow-up "deposits"), mule collection (one account collecting a fixed fee from 10 to 28 victims in 6 to 36 hours), velocity drain (4 to 9 similar payments in minutes after a remote-access app is installed) and account takeover (failed logins, a new device, mostly at night, most of the balance). Some scam accounts are old (30 to 40 % are 60 to 900 days old), like bought or rented accounts would be. Victims report the payee 10 to 50 % of the time.

Events are replayed in time order, so each feature only uses what was known before that payment. The data is split by time: the first 60 % for training, the next 15 % for calibration and the last 25 % for testing. A random split would leak future behaviour into training.
