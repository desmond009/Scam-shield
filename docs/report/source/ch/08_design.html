System Design and Technical Details

System Architecture

ScamShield is a service-oriented system of six containers orchestrated with Docker Compose docker (Figure 8.1). The design separates the hot path — everything that must happen before the payer sees a decision — from asynchronous work that must not slow the payer down (alerts, baselines, reputation, metrics, retraining).

Integrations in a real deployment. ScamShield would sit inside a PSP's or bank's UPI app back end: the app calls check before invoking the UPI collect/pay flow, and confirm is replaced by the institution's own UPI pay call guarded by the check token. Optional external signals: DoT FRI for the payee's mobile number, the I4C Suspect Registry, and the bank's own FRM case system.

Algorithms and Business Rules

Feature computation

Twenty features are computed from a common FeatureInput by identical TypeScript and Python implementations driven by a shared JSON specification; 300 randomised parity cases guarantee that training and serving compute exactly the same values. Key definitions:

  • Amount z-score against the user's 30-day completed payments: z = (a − μ) / max(σ, 0.1μ, 50), clamped to [−5, 20], and 0 with fewer than three past payments. The floor on σ prevents users with very regular payments from producing explosive z-scores.
  • Usual hour is a circular mean: the mean angle of 2πh/24 over past payments, so that 23:00 and 01:00 average to midnight rather than noon. The deviation is the circular distance in hours.
  • Velocity counts completed payments in the previous 10 minutes and 1 hour from Redis sorted sets; split payments counts payments to the same payee in the last hour within 20 % of the amount.
  • Mule signal: distinct other users who paid the payee in the last 24 hours; payee age: days since the payee was first seen.
  • Context: three binary questionnaire features (0 until answered).

Machine-learning model

The model is scikit-learn's HistGradientBoostingClassifier — a histogram-based gradient-boosted tree ensemble friedman2001 — with 300 iterations, learning rate 0.08, 31 leaves per tree, L2 regularisation 1.0 and balanced class weights. Class weighting and boosting distort probabilities, so the raw scores are calibrated with isotonic regression zadrozny2002, niculescu2005 fitted on a separate, later time slice. The calibrated probability × 100 is the ML score. A class-weighted logistic regression is trained as a sanity-check baseline.

Explanations by occlusion. For each decision the service builds a batch of 21 rows — the original feature vector and 20 copies in which one feature is reset to the value of a typical legitimate payment — and predicts them in one call. The drop in fraud probability for each feature is its contribution; the top three (if above 0.5 percentage points) are returned to analysts. This is model-agnostic and costs one batched prediction.

Blending, bands and overrides

FinalScore = clamp[0,100]( wR · RuleScore + wM · MLScore ), wR = 0.4, wM = 0.6

  • If the ML service is unavailable, FinalScore = RuleScore and the decision is marked degraded.
  • Bands: LOW if FinalScore < 35; MEDIUM if 35 ≤ FinalScore < 70; HIGH if FinalScore ≥ 70.
  • Override 1 — payee confirmed as fraud by an analyst: FinalScore ← max(FinalScore, 95); payment BLOCKED.
  • Override 2 — user reports being asked for an OTP or to install an app: FinalScore ← max(FinalScore, 70).
  • Questionnaire re-score: FinalScorenew ← max(FinalScorenew, FinalScorebefore) — answers can never lower the score.
  • Reasons are ordered: overrides, then rule hits by points, then “matches known scam patterns” if MLScore ≥ 50. Users see the top three.

Resilience and consistency algorithms

  • Circuit breaker nygard2018: failures of the ML call are counted in Redis over a 30-second window; at five failures the breaker opens for 15 seconds (ML skipped). Afterwards a single probe request, elected with an atomic SET NX lock, closes the breaker on success or re-opens it on failure. Because the state lives in Redis, all API instances share it.
  • Idempotency kleppmann2017: the Idempotency-Key is claimed with SET NX for 24 hours; a retry with the same key and body replays the stored response, a different body returns 422, and a concurrent duplicate returns 409. A unique database index is the second line of defence.
  • Atomic confirm: in one database transaction, UPDATE transaction SET status='COMPLETED' WHERE id=? AND status='PENDING' (exactly one concurrent confirm can win) and UPDATE user SET balance = balance − amt WHERE id=? AND balance ≥ amt (balance can never go negative), followed by ledger entries. Any failure rolls back everything.
  • Check token: an HS256 JSON Web Token rfc7519 valid for 10 minutes, binding user, transaction, amount and payee, so a client cannot skip or alter the risk check.

Synthetic Data Generation

Because real labelled fraud data is not available to students, we wrote a seeded generator (default seed 42) that simulates 150 users for 120 days (30-day burn-in, 90 days written out, ≈ 165,000 payments). Its design goal is realism that makes detection hard, including legitimate behaviour that looks suspicious.

Scam accounts are not all new: 30–40 % are 60–900 days old, as bought or rented accounts would be. Victims report the payee 10–50 % of the time, 1–48 hours later. Features are computed by replaying events in time order with no look-ahead, and fraud-labelled payments are excluded from baselines, exactly as in the live API. The data is split by time: first 60 % for training, next 15 % for calibration, last 25 % as the holdout.
