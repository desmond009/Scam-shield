Implementation

What We Built

All the code is in one repository. TypeScript packages are managed as npm workspaces and the ML service is a separate Python package. There are five main parts.

Shared risk core (packages/shared). This is a small library with no side effects. It turns inputs into the 20 features, runs the rules, blends the scores, applies the overrides and builds the reason text. Since it is pure logic, it was easy to test thoroughly, and both the API and the browser use exactly the same code. The main decision function is in Appendix C.

ML service (services/ml). On first start it generates the data, trains the model and a logistic regression baseline, calibrates, evaluates all three systems on the test period, and saves a versioned model folder before it starts serving. The /score endpoint rejects requests that do not have exactly the 20 expected features, and returns the probability, the score, the model version and the top contributing features. Retraining runs in the background. Analyst labels are only ever added to the training data, never to the test data.

API (apps/api). The feature builder fetches everything it needs with one PostgreSQL query plus a batch of Redis reads running in parallel. The risk engine calls the shared core and the ML client, saves the decision with its latency and model version, and queues a job. The payments service handles the idempotent check, re-scoring after the questions, cancel and report, and the atomic confirm. Middleware handles sessions, roles and rate limits, and every route validates its input.

Worker. This creates alerts for MEDIUM and HIGH decisions and publishes them for the live analyst view. It also refreshes a user's baseline after each payment, recalculates payee reputation, writes a metrics summary every 30 seconds (which also tells the health page that the worker is alive), syncs the active model every minute and runs retraining when asked. Failed jobs are retried, and if the queue is down, payments still go through.

Web app (apps/web). For users, it has the wallet, the Send money flow with the risk meter, reasons, questions and the MEDIUM/HIGH screens, and a My Safety page. Analysts get a live alert queue and a detail view. Admins get the scam simulator, the rules editor with what-if preview, the model evaluation page and the system health page.

Development Method

We worked in seven short phases, P0 to P6, and each ended with something working, tested and committed. Before writing any code we agreed on a "definition of done", which included the evaluation rule from Chapter 1: the hybrid had to beat rules alone on recall at the same false alarm rate, and if it did not, we would say so. We did the riskiest part (data, model and evaluation) first.
