Implementation

The system is implemented as a single monorepo with npm workspaces for the TypeScript packages and a Python package for the ML service. The repository contains 134 TypeScript/TSX source and test files and 17 Python files. This chapter describes each module, the development process and the working product.

Shared risk core (packages/shared)

The heart of the system is a pure, side-effect-free library: computeFeatures() turns a FeatureInput into the 20 features; evaluateRules() applies the enabled rules with their weights; decide() blends rule and ML scores, applies overrides and orders reasons; and the reason catalogue renders each reason as a user sentence, a summary phrase and an analyst detail. Because the logic is pure, it is exhaustively unit-tested and identical in the API and the browser. Appendix D reproduces the decision function.

ML service (services/ml)

On first start the service runs the generator, trains the gradient-boosting model and a logistic-regression baseline, calibrates on the calibration slice, evaluates rules-only, ML-only and hybrid on the holdout, writes a versioned model directory (model.joblib, metrics.json, evaluation.json) and only then begins serving. POST /score validates that exactly the 20 named features are present, returns the calibrated probability, the 0–100 score, the model version and the top contributing features. Retraining runs in the background with progress exposed at /train/status; analyst labels are added to the training data only, never to the holdout.

API (apps/api)

The feature builder gathers all inputs in one PostgreSQL round trip plus pipelined Redis reads executed in parallel, falling back to PostgreSQL to rebuild known-payee and device sets on a cache miss. The risk engine calls the shared core and the ML client (with timeout and circuit breaker), stores the decision with its latency and model version, and enqueues a job. The payments service implements idempotent check, questionnaire re-scoring, cancel-and-report, and the atomic confirm with check-token verification, cooldown and retype checks. Middleware provides session/bearer authentication, role checks and Redis rate limiting; every route validates input with zod and logs with a request ID.

Worker (apps/api/src/worker.ts)

Consumes two BullMQ queues: risk-events (create or escalate alerts for MEDIUM/HIGH and publish live events; refresh the payer's baseline after each completed payment; recompute payee reputation; 30-second metrics roll-up that doubles as the worker heartbeat) and model (sync the active model every 60 seconds; retrain on request). Jobs retry with exponential back-off; enqueue failures are logged and never block payments.

Web application (apps/web)

  • User: landing page with one-click demo accounts; wallet dashboard (balance, 30-day spending chart, recent transactions); Send money with recipient card, risk meter, reasons, questionnaire and the MEDIUM/HIGH interventions; My Safety (warnings received, payees reported).
  • Analyst: live alert queue with filters and a “Live” indicator (SSE); alert detail with score breakdown, reasons, ML top features, features table, payee panel and review form.
  • Admin: Scam Simulator; Rules & Thresholds with what-if preview; Model & Evaluation (comparison table, PR curves, threshold sweep, calibration, feature importance, confusion matrices, per-scenario table, retraining); System Health.

Development Methodology

We followed an incremental, Agile-inspired process organised as seven phases (P0–P6), each ending with a working, tested increment and a commit. Before any coding, we fixed a written definition of done that included an honest-evaluation criterion: the hybrid must beat rules-only on recall at a matched false-positive rate, and if it did not, the report would say so. Phases were sized so that the riskiest parts — data, model and evaluation — came first.

The core build (P0–P6) was completed in an intensive one-week sprint beginning 14 October 2026, followed by load testing, a data-leak investigation, demo rehearsal and the preparation of this report. Figure 9.1 shows the timeline.

Daily practice: short stand-ups to agree the day's increment; trunk-based development with one commit per phase; tests written alongside code (integration tests against real PostgreSQL and Redis rather than mocks); every evaluation result checked against feature importances before being accepted (Section 11.1).
