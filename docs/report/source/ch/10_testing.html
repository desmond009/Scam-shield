Testing and Results

Testing Strategy

We tested at several levels. Unit tests cover the shared risk core (features, rules, blending, bands, overrides, reason text). A parity test runs 300 random inputs through both the Python and TypeScript feature code and checks they match exactly. Integration tests run the API against real PostgreSQL and Redis with a fake ML service, because things like double spending and the circuit breaker only show up with real databases. These cover login and roles, the feature builder, the two-step payment, idempotency, parallel confirms, tampered tokens, the pause, the questions, blocking, reports, ML failure and worker jobs. The ML service has its own tests for the scoring contract, input checks and speed. Two Playwright browser tests cover a normal payment and a scam payment from start to end, and we load tested the check endpoint with autocannon.

On 7 November 2026 we ran the unit, parity, integration and ML suites again on a fresh copy of the code, and all 341 tests passed (309 in the shared package, 24 API integration tests and 8 ML tests). The two browser tests need the whole Docker stack running, and they last passed during phase P6. The load test was run on 14 October 2026.

Model Results

The reference model was trained on 96,118 payments and calibrated on 22,734. It was then tested on the last 25 % of the timeline: 45,387 payments, of which 779 (1.72 %) are scams. This includes a festival period it never saw during training. With so few scams, accuracy and ROC-AUC look good for almost any model, so we mainly use precision, recall, false positive rate (FPR) and the area under the precision-recall curve (PR-AUC) saito2015.

The main check from our definition of done was recall at the same false alarm rate. Rules alone run at an FPR of 3.71 %. If we set the hybrid's threshold so its FPR is about the same (3.65 %), it catches 745 of the 779 scams (95.6 %), compared with 571 (73.3 %) for rules alone. So the hybrid passed.

It did not win on everything, though. ML alone ranks payments a bit better than the hybrid (PR-AUC 0.946 against 0.933) and has slightly higher recall at 35. Adding the rules costs a little ranking quality. What we get back is readable reasons, the hard overrides, a system that still works when ML is down, and at our chosen thresholds the best precision and the fewest false alarms. At the HIGH threshold of 70 the hybrid's precision is 96.0 % with an FPR of only 0.056 %, which is why we felt comfortable adding strong friction there. We think this is the right trade for a system that interrupts real people, but it is a trade-off, and the Model page in the app shows it.

By scenario, the hybrid catches 91 % of impersonation, 99 % of mule collection, 89 % of velocity drain and 99 % of account takeover payments (Figure 10.2). Rules alone do worst on account takeover (57 %), where it is the combination of signals that matters. On false alarms, the hybrid flags 0.04 % of everyday payments and 1.0 % of festival payments. It flags none of the shopkeeper supplier batches, while rules alone flag 11.6 % of them. Its weak spot is first payments to new contacts (21.7 %, out of 60) and new merchants (31.3 %, out of 16). These are small groups, but they are the genuine payments that look most like scams.

Calibration improved the Brier score from 0.0046 to 0.0035. The calibration curve shows the model is over-confident between about 30 % and 60 % on the test period, probably because of the festival period, and those ranges have few payments. The most important features (Figure 10.3) are payee age, amount z-score, number of different senders to the payee in 24 hours, and repeated similar amounts. These are reasonable signals, the same kind real fraud teams look at.

Performance

We sent 1,200 check requests at 20 per second over 60 seconds. Every one ran the full pipeline with ML, and there were no errors or fallbacks. Measured from the client, the median was 42 ms, the 99th percentile 118 ms and the slowest 147 ms. The API's own metrics gave a p95 of 109 ms, well under the 300 ms target. The first time we ran this test it went badly: the ML service could only do about 47 requests a second, the circuit breaker kept opening and most decisions fell back to rules. The cause was scikit-learn's thread pool, which costs more to start than a single prediction takes. Setting OMP_NUM_THREADS=1 took the ML service to about 154 requests a second, and the breaker stayed closed. The 20 per second limit came from our per-user rate limit and the 12 test accounts. It is not the most the system can handle.

User Feedback

We planned user acceptance tests around the four personas. Each participant makes three normal payments, pays a "KYC desk" while one of us acts as a pushy caller, pays a large amount to a known person (rent), and then reviews the alerts as an analyst. A session passes if the normal payments go through with no prompt, the participant can explain in their own words why the payment was flagged, they cancel the coached scam payment, and they find the HIGH screen acceptable.

This report does not include results from formal user acceptance sessions with outside participants. These sessions are planned as part of the pilot (Section 12.1).
