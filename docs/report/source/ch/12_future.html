Future Scope and Roadmap

Planned Improvements

The most important next step is testing on real data. We would run ScamShield in shadow mode with a partner, scoring real payments without showing anything to users, then compare the scores with confirmed fraud cases and re-tune the thresholds and calibration. On the detection side we want to use the network of who pays whom to find mule rings, add device fingerprinting, and use outside signals like DoT FRI for the payee's phone number. We also want to watch for drift and get alerts when the model starts to go stale. For safer model updates, a new model should first score live traffic in the background (shadow deployment) and only replace the old one once it is proven.

For the warning screens, we would like to test different wordings with real users. We would also like to add a "trusted contact" confirmation for senior citizens on HIGH payments, vary the warning design so people do not get used to it anderson2015, and add Hindi and Kannada with voice read-out. For analysts, it would help to group cases by payee and export them to the bank's own systems. Federated learning could let banks share fraud patterns without sharing customer data.

Scaling Plan

The API and ML services keep no state of their own, so we can run more copies behind a load balancer. For a pilot at a few hundred requests a second, three API and three ML copies with managed PostgreSQL (plus a read replica) and Redis in an Indian region should be enough. At a few thousand requests a second we would move to a Redis Cluster with each user's keys kept together, split the transaction tables by month, and autoscale the ML service. At national scale it would make sense to move to Kafka for events, add a proper feature store so that training and serving always match, and run in more than one region.
